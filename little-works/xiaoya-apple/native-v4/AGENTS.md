# Xiaoya LifeLab / Native V4 — Product and frontend rules

Scope: `little-works/xiaoya-apple/native-v4/`, the **judge-facing app** in `ndshuge/xiaoya-lifelab`. This app is **小芽**, a student life and personal growth companion, **not 知序 AI 学院**.

## Product and information architecture
- Keep the three top-level destinations: **今天 / 事项 / 发展**. Inside 事项: real calendar events, dated deadlines, undated inbox. A deadline is **not** a scheduled study block. Inside 发展: mood/journal and goals. Preserve the single original Xiaoya avatar as the assistant entry.
- Minimize duplicate actions, repeated labels, inflated empty summaries and faux dashboard scores. A new task must remain quick; advanced fields are opt-in. Journal and mood are private local data; no automatic AI upload.
- **Secondary navigation (2026-11-03)**: on mobile, `设置` and `搜索` are pushed destinations, never fourth/fifth tabs. Hide the bottom Dock **and its progressive blur edge** while a secondary view is open, turn the existing upper-right overflow control into a calm, >=44px `完成` dismissal (search uses `返回`), and restore the last primary screen, scroll state and unsaved journal draft. The Xiaoya avatar remains the only assistant trigger; do not replace it with a back button. Desktop keeps its sidebar. Keep route updates synchronous and interruptible; reduced-motion and WebKit must work.
- Retain judge demo vs personal-mode separation, original V3 archive, data export/import, the mature growth route and explicit AI authorization.

## Apple-inspired design decisions — verified scope
- Apply **clarity, content-first hierarchy, predictable navigation, direct manipulation and restraint**. Preserve the original Xiaoya illustration and system/PingFang CJK typography. Use grouped rows/hairlines rather than stacks of look-alike cards.
- Material tiers: opaque content (L0), purposeful overlapping dock/dialog frost (L1), true optical displacement only when an actual licensed shader has been integrated **and proven across WebKit/Chromium** (L2). CSS `backdrop-filter` alone is **never L2**. Avoid double white haze or stacking independent scroll-edge effects.
- Interactive targets use **at least 44×44 CSS px** (as a web test approximation; not a claim of iOS native-point parity). 64×28 visible switches must have ≥44px *actual native input* hit height. Keep `:focus-visible`, associated labels, keyboard Escape, return focus and scroll unlock.
- Mood picker: one unified 5-option choice surface, never five separate decorated cards. Preserve labels, pressed state, and visible “未保存” feedback until the user commits the day’s journal; do not silently upload or autosave a private mood entry.
- Motion is functional: down/hold/release/cancel, opening and closing from the same origin, interruption, repeated taps and Reduced Motion. Avoid layout-shifting scale and independent motion of the dock.
- **Interactive hitbox stability:** do not animate `transform` on the live `#workspace` during navigation: the visual slide moved real input hitboxes 10px at the start of the transition. The old, inert painted snapshot may move; the new live view must keep final geometry from frame one. Assert this in `qa-v4-motion-dock.cjs`.
- **V4 navigation motion (2026-11-04 latest)**: route DOM and active-tab state update synchronously. **Never clone or overlay the outgoing page or use `.xy-route-ghost`**; user's iPhone Safari recording shows visible content afterimages. Keep exactly one live `#workspace`; only a small transform on the new heading may animate, and never transform live interactive hitboxes. Retain per-tab scroll, drafts and keyboard focus. Support immediate reversals, WebKit and Reduced Motion.
- **2026-11-04 Academy navigation revision (supersedes headline-only motion above where consistent with hitbox safety)**: On the three primary destinations, allow pointer-led horizontal swipes with directional, non-interactive paint-only feedback and a 0.8-damping / 0.3-second spring release. Swipe must never move the active `#workspace` or duplicate live content. Forward/back navigation, settings, search and segmented pages may animate the **new** page's clip-path + opacity in place, keeping its interactive geometry fixed from frame one. Assistant opening and closing can use its own local transform (without moving workspace or Dock), must settle on rapid reversal and return focus. Normal sheet editors may softly fade if no source card exists. Disable decorative motion with Reduced Motion; protect scrolling, text selection, keyboard, edge-pop and timeline input. Preserve all original Agent permissions and data.
- **2026-11-05 two rigid pages + top assistant (latest)**: The user explicitly wants two complete pages traveling together, with the old page fully sliding out while the new one slides in; page interior content remains static relative to its own page. Supersedes old paint-only arrows, page clips, and staggered child opacity. A temporary inert outgoing *real* DOM node during click navigation is allowed (never a clone), and an inert prefetched target page is allowed during touch drag, provided exactly one target is operable, old layers are cleaned up after ~315ms, and Dock, mood assets, data and Agent stay intact. Chat panel enters from fully offscreen above and closes along precisely the reverse path, without scale. Validate edge/scroll/reversal/Reduced Motion/WebKit and performance; do not claim real-device Safari until tested.
- **2026-11-05 V5.7 physical spring refinement (latest, supersedes 305/315ms timings)**: Keep both full pages with fixed internal layout, but let a shared physically sampled transform run ~690ms for click navigation and up to ~760ms for touch release; preserve in-flight translation on rapid opposite navigation in Edge/WebKit. Xiaoya avatar is a toggle (tap again closes), the assistant header identity closes too. Assistant rises from full above-screen origin with ~780ms damped spring, exits upward with ~610ms spring; no scale. Normal bottom sheet emerges from below on ~750ms spring and leaves downward ~530ms; source-linked Magic Move remains unchanged. No Dock edits, no private data/schema changes, and reduced-motion remains instantaneous. Confirm in actual device before claiming true iPhone Safari QA.
- On mobile text focus, keep the ordinary floating Dock and assistant geometry stable; hide the Dock only when the visual viewport actually becomes keyboard-occluded. Reposition the assistant/editor only after `visualViewport` reports genuine keyboard-sized occlusion (>=120 CSS px); focus alone must **never** move the open assistant panel. Interrupt the panel entrance animation when the keyboard starts covering the composer. Use synchronous `visualViewport.resize/scroll` updates for alignment, with reduced-motion and desktop fallbacks.
- Test iPhone safe area, browser toolbar, content underlay, open virtual keyboard, 200% zoom and long Chinese strings. **WebKit simulation is not real iPhone Safari**.
- First paint must remain meaningful **before ES modules hydrate**: privacy-safe, non-shimmer structural placeholder without fake tasks, and an explicit retry when module loading fails. Keep the original judge query on retry. Test intentionally delayed and failed module requests in Edge and WebKit; do not infer iPhone Safari performance.
